# 天堂客户端容器格式规范 · `Text.pak` / `Text.idx`

> 版本：v1（2026-10-19）｜依据：`pak_parser\paktools.py`（源自 l1j-en Launcher 的 PakTools.cs）+ 对本服 `龙潭天堂\Text.pak/idx` 的实测
> 用途：**热更合并器**（Rust `l1pak` / Python `l1eat`）的唯一权威依据。改实现前先改这里。

---

## 一、两个文件的关系

```
Text.idx  =  "目录"：告诉客户端每个条目叫什么、在 pak 的第几字节、多长
Text.pak  =  "数据"：所有条目首尾相接（中间允许有未引用空隙）
```

**必须成对部署**：只换一个 → 客户端报 `Can't load string table.`（2026-10-17 已踩过）。

---

## 二、`Text.idx` 结构

```
偏移 0   : UInt32  n            记录条数（明文）
偏移 4   : N × 28 字节          每条记录，整段被 Encode 加密
文件长度必须 == 4 + n × 28       （实测 692,528 = 4 + 24,733×28）
```

单条记录（28 字节，解密后）：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0 | Int32 | 该条目在 pak 中的偏移 |
| +4 | 20 字节 | 条目名（UTF-8/latin1，NUL 填充，**最长 19 字符 + NUL**） |
| +24 | Int32 | 该条目字节数 |

> 实测：24,733 条、**重名 0 条**、越界 0 条、最长名字 19 字节。

---

## 三、加密算法（Encode / Decode）

- **分组**：8 字节一块，**块与块之间完全独立**（无链式依赖）
- **密钥**：5 张静态表 `Map1~Map5`（`maps.json`，Base64 内嵌资源，来自 PakTools.cs）
- **单块过程**：`Map1` 查表 → 16 轮 `_sub_403340`（奇偶方向不同）→ 半块交换 → `Map2` 查表
- **尾部余数**：`len % 8` 的那几个字节**原样复制，不加密**
- **起始位置**：
  - `Text.idx`：从**偏移 4** 开始（前 4 字节条数明文）
  - `Text.pak` 的每个条目：从**条目自身第 0 字节**开始

**不要自己实现这套算法**——Python 用 `paktools.encode/decode`，Rust 侧按本文件移植并逐字节对拍。

### 实测证据（2026-10-19）

| # | 检查项 | 结果 |
|---|---|---|
| 1 | `4 + n×28 == idx 长度` | ✅ 692,528 |
| 2 | idx 正文解密 = n×28 字节 | ✅ 692,524 |
| 3 | 条目越界/负偏移 | 0 |
| 4 | 重名条目 | 0（最长名 19 字节） |
| 5 | pak 覆盖率 | 99.917%（16,881,564 / 16,895,621），空隙 3 段共 **14,057 B**，最大 13,780 B |
| 6 | `encode(decode(seg)) == seg` | 200/200 一致 |
| 7 | `size % 8` 尾巴是否原样 | 300/300 原样 |
| 8 | 改 1 个明文字节 → 密文变化 | **恰好 8 字节（1 个块）** ⇒ 块独立性成立 |

第 8 条是整个热更方案的地基：**改一个块，只动 8 个字节，其余块可原样搬运。**

---

## 四、条目数据的布局

- pak 里**没有长度前缀**，每条的长度完全由 idx 给出
- 条目之间**允许有未引用的空隙**（本服当前只有 14 KB，历史版本曾出现 **7.45 MB** 中部空洞）
- 条目在 pak 中的物理顺序与 idx 顺序**无关**

---

## 五、三条铁律（违反即出事）

1. **绝不"紧凑重建"**：把条目按顺序重新拼一遍=丢掉所有未引用空隙。历史上 26 MB 那版 `Text.pak` 有 7.45 MB 空洞，重建后直接从 26,052,619 掉到 18,600,502，客户端行为无法保证。
2. **`idx` 与 `pak` 任何时候必须自洽**：写完 pak 再改 idx，中间崩溃 = 客户端读坏。必须"写临时文件 → 校验 → 原子替换"。
3. **条目名不改**：名字是客户端索引键；新增条目要插一条 idx 记录（本工具暂不支持新增，只支持替换）。

---

## 六、三种写入策略

| 策略 | 条件 | pak 变化 | idx 变化 | 适用 |
|---|---|---|---|---|
| **A 原地写** | 新内容长度 **==** 旧长度 | 只变变化的 8B 块 | **0 字节** | 改文案（最常见） |
| **B 尾部追加** | 长度不同 | 末尾 +新内容，旧数据保留 | **1 条记录**（offset/size） | 改页面、换图标 |
| C 紧凑重建 | — | 整个文件重写 | 全部偏移重排 | ❌ **禁止** |

`l1eat` 的 `build` / `apply` 采用 **A → B 自动降级**：长度相同走 A，不同走 B。

---

## 七、版本与校验

- 每个条目的"内容指纹"用 **明文的 SHA-256**（不是密文），这样发版端与客户端算的是同一个值
- 清单（`manifest.json`）记录：`{name, size, sha256}` + 全局 `version`
- 签名：**Ed25519**（私钥仅存发版机，公钥编译进登录器）
